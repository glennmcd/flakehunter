# GitLab host and CI source values

**Status:** Brief, for review. No code changes until this is agreed.

flakehunter-airflow is adding a DAG that uploads GitLab CI results through `POST /api/v2/reports`
([its plan](https://github.com/glennmcd/flakehunter-airflow/blob/main/docs/plans/gitlab-ingest.md)). It needs
FlakeHunter to accept a repository with host `gitlab` and runs with CI source `gitlab_ci`. Today both are refused:
`REPO_HOSTS` is `["github"]`, `CI_SOURCES` is `["github_actions"]`, and the database check constraints and
`docs/openapi.v2.json` say the same. This is item 1 of "Remaining work" in [ci-source-adapters.md](ci-source-adapters.md).

The model already allows it ([ADR 0011](../decisions/0011-repository-hosts-and-ci-sources.md)): repositories are
unique per `(host, external_repo_id)` and `(host, full_name)`, runs per `(repo, ci_source, ci_run_id, run_attempt)`,
and `resolveRepo` handles a path registered on two hosts. Only the lists of allowed values change.

## What changes

| Where | Change |
|---|---|
| `packages/shared-types/src/domain.ts` | `REPO_HOSTS = ["github", "gitlab"]`, `CI_SOURCES = ["github_actions", "gitlab_ci"]`, `DEFAULT_CI_SOURCE.gitlab = "gitlab_ci"` |
| `apps/api/src/db/schema.ts` | `repos_host_check` and `workflow_runs_ci_source_check` built from `REPO_HOSTS` and `CI_SOURCES` instead of literal lists, so the constants and the database cannot drift apart again |
| `apps/api/src/db/migrations/0006_*.sql` | generated by `db:generate`: drops and re-adds both constraints with the wider lists |
| `apps/api/src/routes/api/reports.ts` | the upload description says the default is "github_actions for GitHub, gitlab_ci for GitLab" |
| `packages/shared-types/src/api/v2/reports.ts` | the same wording in the `X-FH-CI-Source` comment |
| `apps/api/src/plugins/openapi.ts` | `API_CONTRACT_VERSIONS[2]` from `2.0.1` to `2.1.0` |
| `docs/openapi.v2.json` | regenerated with `bun run openapi`: the `X-FH-CI-Source`, `ciSource` and `host` enums gain the new values |
| `CLAUDE.md`, `ci-source-adapters.md` | registering a GitLab project; "Remaining work" item 1 marked done |

`DEFAULT_CI_SOURCE` is typed `Record<RepoHost, CiSource>`, so the typecheck fails until the `gitlab` entry exists.
`seed-dev-repo.ts` and `create-repo-token.ts` validate against `REPO_HOSTS` and need no change: a GitLab project is
registered with `SEED_REPO_HOST=gitlab`, its numeric project id as `SEED_REPO_EXTERNAL_ID`, the namespace (which may
be nested, `group/sub`) as `SEED_REPO_OWNER`, and its token is minted with `TOKEN_REPO_HOST=gitlab`. The seed script
already skips `github_installations` for hosts other than `github`.

## What does not change

- **No GitLab adapter.** A `CiSourceAdapter` is only used by the webhook path to fetch artifacts. GitLab data arrives
  through `POST /api/v2/reports`, which needs no adapter. The registry keeps one adapter, and `ciSources.get("gitlab_ci")`
  is never called. A GitLab webhook is a separate piece of work.
- **No check that the CI source suits the host.** A GitHub repository may upload `gitlab_ci` runs (a mirror built on
  GitLab) and the reverse, as ADR 0011 intends. Only the defaults are per host.
- **The dashboard.** It shows neither host nor CI source, and uploaded runs have no `htmlUrl`, so nothing links to
  GitHub by mistake.
- The GitHub webhook, `github_installations`, the API's routes and its other schemas.

## Versioning

- **Spec:** `2.1.0`. New request values are compatible. New values in response enums (`ciSource`, `host`) are
  compatible for clients that accept unknown values but not for ones that validate enums strictly. The only known
  client, flakehunter-airflow, parses no success bodies on upload and re-pins on purpose; its drift check opens an
  issue when this spec is published.
- **Release:** one `feat(api): accept GitLab repositories and gitlab_ci runs` commit, so release-please proposes
  `0.5.0`. flakehunter-airflow re-pins to that tag.
- **Database:** migration 0006 only widens two constraints; existing rows already pass. Run `bun run db:migrate`
  against Neon before deploying the API, as with 0005. Deploying the API without the migration fails a GitLab
  registration or upload with a constraint error and affects nothing else.

## Tests

- `resolveRepo.test.ts` currently drops `repos_host_check` to fake a second host. It now seeds a real `gitlab`
  repository and keeps the constraint.
- A schema test: every `REPO_HOSTS` and `CI_SOURCES` value can be inserted, and an unknown value is refused by each
  constraint.
- Upload tests in `versions.test.ts` (or `routes.test.ts`):
  - with a `gitlab` repository's token and no `X-FH-CI-Source`, the run is stored as `gitlab_ci`;
  - with `X-FH-CI-Source: gitlab_ci` on a GitHub repository, a run with the same id as a `github_actions` run is a
    separate run, not a duplicate;
  - an unknown CI source is still a `400`.
- `GET /api/v2/repos` lists the GitLab repository with `host: "gitlab"`, and `?repo=gitlab:group/sub/project` resolves it.
- The existing suites, `openapi:check`, lint, typecheck, `build:web` and `synth:infra` pass. `db:generate` reports
  no changes after 0006.

## Risks

- Building the constraints from the constants changes how Drizzle renders them; if its output differs from the
  current text in ways that are not just the list, the 0006 migration is checked by hand before it is committed.
- A strict client of `GET /api/v2/repos` or the test history endpoints would reject a `gitlab` or `gitlab_ci` value.
  None is known.

## Open question

Should `gitlab` and `gitlab_ci` go in together, or `gitlab_ci` alone so a GitHub repository can upload GitLab runs
first? The airflow plan registers GitLab projects as `gitlab` repositories, so this brief adds both.
